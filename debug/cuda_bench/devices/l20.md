Run logs, CSVs and reference outputs are kept in `/root/gpu_port` and `debug/cuda_bench/results` until the end of the deployment (section 11.8); the tables and verdicts of the sections below are their record.

## 2. Environment of the image

- The image holds the locales `C`, `C.utf8` and `POSIX` only. Under an `LC_ALL` it lacks, conda Python crashes in `import readline`, so pytest exits with status 139 at startup; jobs run under `LANG=LC_ALL=C.UTF-8`.
- Ubuntu's bash sources `~/.bashrc` for a `bash -c` started by sshd, and that file activates conda base, which exports conda's compiler and linker variables (`CFLAGS`, `CXXFLAGS`, `LDFLAGS`, `CMAKE_ARGS`, `CMAKE_PREFIX_PATH`, `NVCC_PREPEND_FLAGS=-ccbin <conda g++>`, `CONDA_BUILD_SYSROOT`). Jobs start through a launcher that unsets the SSH variables, runs `bash --norc` and refuses to start when any of these variables is set. The builds above have empty `CMAKE_*_FLAGS`, no `-ccbin`, `--disable-new-dtags` or conda sysroot in their `build.ninja`, and RUNPATH entries only.
- The suite `test_dpa4c_cpu.py` runs its 50 cases only with `DEVICE=cpu`; on a GPU node it otherwise skips 41 of them.

## 3. Phase A

Baseline `37a3fa54c`, mandatory test environment: CUDA descriptor suite 862 passed (619 s), with `DP_DPA4C_TYPE_SLOTS=0` 862 passed (386 s), CPU suite 50 passed (`DEVICE=cpu`), model, freeze and serialization suite 166 passed and 2 failed. The two failures (`test_zbl_bridging.py::TestZBLBridgingExportAndTraining::test_graph_freeze_and_deep_eval_parity` and `::test_native_spin_with_bridging_graph_freeze_and_deep_eval`) are the AOTInductor freeze failure of integer `xp.clip` below; with its fix the model suite passes 168 of 168.

The freeze failure: before version 1.14, array_api_compat serves `clip` for torch through its generic implementation, which selects the elements to replace by `(x < bound) | isnan(bound)`. For an int64 array, the Triton kernel that AOTInductor generates on CUDA evaluates that `isnan` with `libdevice.isnan` on int64, which Triton 3.7.1 does not define (`KeyError: (triton.language.int64)`). Commit `6fcfc1819` (`fix(dpmodel): bound integer indices without clip`) bounds the three integer indices with `maximum` and `minimum` instead; the outputs are bitwise unchanged.

## 4. Possible upstream issue: a DPZBL `.pt2` without ghost atoms

Not hardware- or version-specific and outside this campaign; recorded for the user. A DPZBL model (DPA1 with a pair table, nlist lower) freezes, but its `.pt2` fails at inference when the extended system has no ghost atom within the cutoff, so that `nall == nloc`.

Model and freeze, from the repository root (on CUDA with array_api_compat before 1.14 the freeze needs `6fcfc1819`):

        "axis_neuron": 2,

The native neighbor builder of `DeepEval` passes `extended_coord` of shape `(1, 6, 3)` and `nlist` of shape `(1, 6, 20)`, and the call fails with

```
RuntimeError: Expected Ne(s54, s96) to be True but received 6
```

The exported program (`_trace_and_export`, nlist lower) carries four runtime assertions on these sizes, where `s54` is `nall` (dimension 1 of `extended_coord`), `s96` is `nloc` (dimension 1 of `nlist`) and `s77` is an internal size of the program: `s96 <= s77`, `Ne(s77, s96)`, `s96 <= s54` and `Ne(s54, s96)`. They are the guards of slices of an `nall` axis to `nloc` that the export records from sample inputs with ghost atoms; the export of the baseline code carries the same four. With ghost atoms (16 atoms spread over the same cell, `nall` = 150), the frozen model matches the eager one to 2.8e-12 eV in energy and 1.6e-11 eV/Å in force. Observed with the archive compiled for CUDA; the assertions precede the compilation, so an archive compiled for the CPU carries them as well.

## 6. Tuning decisions

### 6.1 Co-scheduled lockstep blocks

The derived rule stays. LAMMPS A/B, six alternating repeats, ms per step, derived → `DP_DPA4C_COSCHEDULE=0`:

| System | Grade | 10,296 atoms          | 100,800 atoms          |
| ------ | ----- | --------------------- | ---------------------- |
| carbon | Air   | 1.341 → 1.291 (−3.8%) | 12.31 → 12.42 (+0.8%)  |
| carbon | Plus  | 2.262 → 2.370 (+4.8%) | 21.78 → 24.77 (+13.7%) |
| BCN    | Plus  | 2.491 → 2.585 (+3.8%) | 23.27 → 24.88 (+6.9%)  |
| five   | Plus  | 3.260 → 3.139 (−3.7%) |                        |

Air on BCN and five elements, whose slotted scans of 64 channels run blocks of independent rows either way, changes by +0.3% and +0.2%. The model steps of the overrides stage had shown −8.4% and −5.2% for Air because `bench_ops.py` kept the rows of its graph in lattice order, while the lockstep blocks rely on rows sorted by bond length, as the LAMMPS builder writes them; the stage now times graphs with `--order distance`.

Both losses lie in the co-scheduled edge scans. Under Nsight Systems at 10,296 atoms the Air backward on carbon takes 0.504 ms co-scheduled against 0.458 ms in blocks of independent rows, and the eight-slot backward of Plus on five elements 1.143 ms against 1.024 ms, its forward 0.652 ms against 0.629 ms; where co-scheduling wins, it shortens the scans by 1% to 11%. The co-scheduled Air backward, held at 80 registers by its 768 threads, keeps 120 B of local memory against 40 B for blocks of one row. The same source compiled for sm_120 by the same nvcc 12.8 keeps 72 B, and nvcc 12.6, 12.8 and 13.1 generate the same code for sm_89, so the spill follows from the target, not from the toolchain. The eight-slot backward of Plus keeps 120 B against 48 B. No rule on the local memory of the two instances fits every point: the Air kernels that lose at 10,296 atoms win at 100,800 atoms, and the five-element forward loses without any spill.

### 6.2 Fused fitting network

Every compiled fused shape and the per-layer kernels give the same energy and input cotangent bit for bit at every width and run size, so the choice between them affects only time. A local selector patch that forces one shape at a time (never committed) timed all of them with the method of `bench_fitting.py` at 16 run sizes from 512 to 131,072 nodes for the five fitting networks, and the decisions were then checked in LAMMPS (six alternating repeats).

Two rules changed, in `cb14b4562` (`perf(fitting): route the fused fitting by device ridge and wave count`):

- A width that the 128 columns of the per-layer large tile divide (256 here) takes the per-layer kernels at runs of more 32-node panels than multiprocessors when the fp32 ridge of the device lies below width / 4, the FLOP per byte of a hidden layer of those kernels. The L20 (ridge 68.7) and the RTX PRO 6000 (about 70) keep the fused throughput shape, the H20 (ridge 10) takes the per-layer kernels, which shorten its LAMMPS step by 1.2% to 5.6% for Neo and Air on carbon and BCN at 10,296 and 100,800 atoms. At widths 96 and 192 the per-layer large tile wastes a quarter of its columns, and the fused shapes win at every size on the L20 and the H20.
- At a width of 96 the 64-node panels serve a run also when they pass it in fewer waves than the 32-node panels, both counted at the CTAs per multiprocessor that the device keeps resident (two and three here). At 10,296 nodes one wave of 64-node panels (161 of 184 slots) takes 0.064 ms against 0.078 ms for two waves of 32-node panels (322 of 276), and the LAMMPS step of Nano 0.3770 ms against 0.3914 ms on carbon (−3.7%) and 0.4441 ms against 0.4581 ms on BCN (−3.1%); at 21,952 atoms (two waves against three) 0.7088 ms against 0.7229 ms (−2.0%). At 512, 19,968 and 100,800 atoms the step is unchanged within 0.5%. On the H20 the rule is neutral at 17,280 atoms.

The rule change leaves every output bit unchanged on the L20: `bench_ops.py --trained --compare` against the baseline references reports zero deviation for the five grades at the three sizes, the 30 LAMMPS run-0 dumps are bitwise identical, and the DPA1 and DPA4C CUDA suites pass (921 passed, 8 skipped).

The throughput shape of width 256 serves 64-node panels, one CTA per multiprocessor, so its time follows the waves of its grid: ceil(panels / 92) × 0.165 ms on the L20, about 1.22 times faster than the per-layer kernels per full wave. A run whose last wave is poorly filled therefore loses (LAMMPS, fused → per-layer): Neo at 6,160 atoms (fill 0.53) 0.7239 → 0.6418 ms (−11.3%), at 8,000 atoms (0.68) 0.8082 → 0.7379 ms (−8.7%), at 12,320 atoms (0.70) a tie and Air there −2.4%; at 16,224 atoms (0.92) the fused shape wins by 4.2%, and at the benchmark sizes 10,296 (0.875) and 100,800 (0.95) by 4% to 5%. On the RTX PRO 6000 the break-even fill lies between 0.67 and 0.77, and the per-layer kernels have a wave structure of their own, so no device-independent fill threshold separates the two paths; these losses remain open.

Rejected: the latency shape of width 384 at large runs is 11% faster than the per-layer kernels in the isolated benchmark at 100,800 nodes, but lengthens the LAMMPS step of Plus at 100,800 atoms by 2.4% (carbon) to 3.5% (BCN, five elements). Lifting the small-run serve gate at 512 nodes gains 1.2% for Nano and loses for the wider networks, whose latency shapes take 1.4 to 2.1 times the per-layer time there; the gate stays.

Thread-block clusters are not available on compute capability 8.9, so the 512-atom fitting runs on the per-layer kernels (31 to 112 µs, 19% to 33% of the step). A timing-only scratch build that runs the CTAs of each cluster shape as independent CTAs, each computing its column slice and exchanging the slices through the L2 sheet but without barriers, bounds what a cluster emulated in global memory could gain: the fitting at 512 nodes takes 0.46, 0.65, 0.67 and 0.88 of the per-layer time at widths 96, 192, 256 and 384 (three, three, four and four CTAs per panel), and the model step of Nano to Air 6.4% to 7.0% less, that of Plus 4.8% less. The barriers such an emulation needs, about fourteen per pass, are not part of this bound.

### 6.4 Run-time launch choices

The row split, the node-group width and the bond prefetch derive the fastest choice in every measured point (section 5). The bond vectors exceed the 96 MiB of L2 at 100,800 atoms, where the prefetch shortens the model step by 0.6% to 2.8%, and stay within it at 10,296 atoms, where it neither helps nor costs.

### 6.5 Fitting of small systems without clusters

At 512 atoms the fitting runs on the per-layer kernels (section 6.2). Two timing-only scratch builds bound what a cluster emulated in global memory could gain; both run the CTAs of each cluster shape as CTAs of a plain launch, each computing its column slice and exchanging the slices through the L2 sheet:

| Build                        | Barrier                               |  Nano |  Mini |   Neo |   Air |  Plus |
| ---------------------------- | ------------------------------------- | ----: | ----: | ----: | ----: | ----: |
| without barriers, model step | none                                  | −7.0% | −6.8% | −6.4% | −6.4% | −4.8% |
| global barriers, model step  | per-panel counter, cooperative launch | −3.2% | −1.6% | −2.6% | −1.5% | −0.4% |
| global barriers, LAMMPS step | as above                              | −3.2% | −1.7% | −2.9% | −2.7% | +0.9% |

Medians of eight alternating LAMMPS runs at 512 atoms, three or four CTAs per panel; with the barriers the forces equal those of the per-layer kernels bit for bit. The barriers cost about half of the gain, and the emulation would further need the head partials of the peers through global memory, so it is not pursued.

A cooperative launch (`cudaLaunchKernelEx` with `cudaLaunchAttributeCooperative`, or `cudaLaunchCooperativeKernel`) captures into a CUDA graph and replays under CUDA 12.6 with driver 580.105.08: 276 blocks met at a grid-wide barrier in each of 50 replays. A cooperative grid larger than the device keeps resident returns `cudaErrorCooperativeLaunchTooLarge` when launched directly and invalidates the capture when launched under capture (`cudaErrorStreamCaptureInvalidated`), so such a launch has to be checked against the occupancy of the kernel before it is issued.

## 7. Further checks on this device

- Two MPI ranks on the one L20 reproduce the per-atom energies, forces and thermo of one rank bit for bit (run 0, Neo and Plus at 10,296 atoms, carbon and BCN). Open MPI here is not GPU-aware, so LAMMPS turns GPU-aware MPI off.
- A Python process that loads a charge-conditioned compressed DPA4C `.pt2` (for example `source/tests/infer/gen_dpa4c_canonical.py`, or `DeepPot` on its fixture) ends with SIGSEGV at exit, after all its work. The charge-state fold of such an archive is a second AOTInductor package, whose generated wrapper holds `static thread_local std::string g_aoti_last_error`; the first call constructs it and registers its destructor through `__cxa_thread_atexit`. The base environment carries libstdc++ 6.0.29 of the defaults package `libstdcxx-ng 11.2.0`, whose `__cxa_thread_atexit` does not delegate to glibc's `__cxa_thread_atexit_impl` and therefore does not keep the registering library loaded; the wrapper is unloaded at interpreter teardown, and `exit()` then calls a destructor in unmapped code (gdb: `atexit_thread.cc:80`; `LD_DEBUG=files` places the address in the fold's `wrapper.so`). The libstdc++ 6.0.34 of conda-forge `libstdcxx 15.2.0` delegates to glibc, and with it preloaded the process exits normally with identical results. LAMMPS links the system libstdc++ (6.0.30, which delegates) and is not affected.

## 9. Fitting-route table

The branch `wip/route-table` at `db92a95ba` (`perf(fitting): measure the fitting route of compressed DPA4C at freeze time`, on `tune/l20` with the V100 port `78a04fbda` and `3f85325d6`) measures at freeze time which fitting route serves each run size and passes the result to `dpa4c_canonical_compress_energy_force` as its trailing `int[]? fitting_routes`. The tuner (`deepmd/pt_expt/kernels/fitting_routes.py`) splits the run sizes into bands at the wave changes of every compared route (`graph_fitting_route_bands`), times both ends of each band, and bisects over 32-node blocks where the two ends disagree. Each sample is a periodic bulk system of exactly the run size at 0.176 atoms/Å³, timed as CUDA-graph replays of the whole operator after one untimed round, with the capture order rotated over the routes. A route replaces the rules only where the median of its per-capture gains exceeds max(1%, their half-range), on at least three captures. This section records the measurement of the tuner and the tables that it measured. Section 11.6 records the loss of those tables where the board runs at its power limit, the check on replays of one route at a time that the tuner of `f5f9e6a39` performs on the routes that the measurement proposes, and the tables of that tuner.

The bulk systems have the bulk neighbourhood at every size: the mean degree at a 6 Å cutoff is 165.8, 153.8, 164.3 and 164.6 at 512, 2,352, 10,296 and 100,800 nodes, within 4% of the continuum value 159.2; the residual is the shell structure of the lattice. Boxes smaller than twice the cutoff keep their periodic images, an atom's own images included; the GPU search returns the same pairs as the CPU search at 1 to 380 nodes. Numbering the atoms in the LAMMPS bin order instead of at random changes the gains by at most 0.3 points (Neo, 6,160 to 14,000 nodes; Air and Nano), so the order is left random.

The gain is taken within each capture because the clocks ramp after host-only work. In one Mini sample at 1,441 nodes the first two captures ran 17% slow for both routes; the spread of each route's own medians was then 10.6%, while the per-capture gain of the per-layer kernels stayed at 6% to 8%.

Two findings outside the tuner:

- With torch 2.13 an AOTInductor archive cannot pass an empty int list to a custom operator. The table is therefore `int[]?` and absent as None; torch main fills the slot with an empty list instead.
- In one pytest process that has run the DPA4C CUDA file, later in-process `torch.profiler` sessions record no CUDA kernel, so `test_fused_network_matches_the_layer_kernels_bitwise` of the DPA1 file reports 31 of its 32 networks as skipped when the files run in that order. ### 11.6 Route tuner on the installed build

Terms of this section. A route is a way of evaluating the fitting network inside the fused operator: the route of the rules, which the operator takes where a table names none, the per-layer kernels, or a fused shape. The run size is the number of nodes that the operator evaluates in one run. A call of up to 131,072 nodes (the default node tile) is one run, whose size is the number of atoms of the system on one LAMMPS rank. A larger call is split into runs of 131,072 nodes and a tail run, and each run takes the route of its own size. A table names a route for intervals of run sizes. An interval is a range of run sizes on which a table names one route. A band is a range of run sizes between which no compared route changes its number of waves (section 9). A sample is the measurement of the tuner at one run size, on a periodic bulk system of exactly that size (section 9). A capture is one CUDA-graph capture of the operator on a sample, replayed for timing. The gain of a route over the rules is the time of the rules over the time of the route, less one, so that a loss is negative. The tie is a gain of 1%, within which the tuner counts two routes as equally fast. The SM clock is the clock of the streaming multiprocessors of the GPU.

The screen is the measurement of section 9, which alternates the replays of the routes within each capture. A route that the screen proposes for a run size, because its gain exceeds its bound (section 11.6.3), is a candidate. A train is the replays of one route alone, back to back, as the LAMMPS step of a large system runs the operator, timed after a lead-in, the untimed replays of that route that let the clock of the board settle; the train time is the median replay time of the timed replays. The sustained gain of a route is its gain on trains after a lead-in of 3 s. The function `winner` of the tuner is the decision of one sample.

A composition is the set of node types of a sample. The node types of the tuner are drawn at random, node by node, from the first three types of the model (hydrogen, helium and lithium in the benchmark models; fewer for a model of fewer types). A preset is a model that a preset name builds with random weights; the presets of the probes below are native-spin models, like the native-spin archives of the device suite, whereas the trained archives are frozen from the five checkpoints, which are models without spin. A tuned archive carries the table that the tuner measured; an untuned archive is frozen without the tuner, carries no table and takes the rules. A LAMMPS A/B compares the step times of two archives and reports the change of step time, the second over the first less one, so that a longer step is positive.

The device suite (`debug/cuda_bench/device_suite.sh`) ran on the installed build alone on the node, with six repeats per point and archives frozen afresh by the installed package, whose freeze runs the route tuner of section 9. Its stages are those of sections 5 and 8: device report, freeze, test, accuracy, repro, LAMMPS whole step and Newtonian spin step. The first device-suite run, with the tuner of section 9 as installed at `fa9e79a36`, shows that this tuner lengthens the step where the board runs at its power limit (section 11.6.2). The tuner of `f5f9e6a39` therefore checks its candidates on trains (section 11.6.3). The second device-suite run, with the first version of that check, supplies the whole-step table of section 11.6.7. The tables of the final version are given in section 11.6.4 and compared with sustained-gain maps in section 11.6.5. The LAMMPS A/B of section 11.6.6 compares the archives of the preceding version, whose tables name the same routes at its points.

#### 11.6.3 The check on trains

The tuner of `f5f9e6a39` keeps the screen of section 9 and checks on trains what passes it. The screen times the routes in alternating short bursts on a periodic bulk system of exactly the run size, whose nodes have the node types of the tuner. A route other than the rules' is a candidate where its median gain over the rules exceeds its bound, the larger of 1% and the half-range of its per-capture gains.

A sample takes its captures in stages of one, two and four, that is, one, three and seven captures in all. After the first capture it stops only where every route besides the rules' lies more than 4 points below its bound. After three captures it stops where every one of them lies more than 1.5 points from its bound, above or below, and after seven it stops whatever the gains. A departure from the rules therefore rests on at least three captures.

The candidates are tried on trains in the order of their gains, and the first that holds takes the run size; where none holds, the run size stays with the rules. A train is at least nine replays of one route, and its train time is the median replay time; the replays span about 100 ms of device time or nine replays, whichever is larger. They follow a lead-in of at least 500 ms of device time of the replays of that route. In the probe of section 11.6.2 the SM clock reached the other plateau within 0.4 s of each of the two changes of the route, which is shorter than this lead-in. Results at a lead-in of 500 ms still depend on the order of the trains (second version, below).

A candidate is timed in two captures that run the two routes in opposite orders, so that a drift of the clocks largely cancels, and its gain on trains is the median of the two. It is timed first with every node of the first type of the model (hydrogen in the benchmark models), whose descriptor runs the single-type scans, and then on the node types of the sample. A model of one node type has one composition. A candidate holds where its gain on trains is at least −1%, the tie, on every composition, and its check stops at the first composition where it loses by more.

Between two routes of which neither is the rules' (the bisection of a band compares the routes that won at its ends) the trains alone decide, by the mean of the median gains of the two compositions. The record of the freeze states how many samples had a candidate checked on trains and how many of those the trains overturned, that is, where the first candidate did not hold.

Each composition alone admits a route that loses on the other. At a common clock the per-layer kernels save 0.112 to 0.117 ms whatever the node types. At 8,000 nodes, where the SM clock stays within 1.2% of 2,520 MHz, they save 0.112 ms with H and with C and 0.117 ms with H, He, Li and with B, C, N. At the power limit the loss depends on the number of types (section 11.6.2). At 129,536 nodes one type loses 4.5% to 6.3% where three types lose 0.5% to 1.5%, so that a check on the three types of the sample alone accepts a route that loses for a system of one element. The Air checkpoint at 12,320 nodes gains 1.1% with every node carbon and loses 1.4% with the three types of the sample, so that a check on one type alone accepts a route that loses for a system of three elements.

The check on trains reached this form in four versions, and the final commit then changed the stop rule of the screen:

- `0996272f4` (`fix(dpa4c): decide the fitting routes on trains of one route at a time`) times the best candidate of a sample on trains, on the node types of the sample, in two captures. It requires both gains above zero and their mean above 1%. It removes the four losses of section 11.6.2 and keeps the gains at 8,000 nodes (the native-spin step of Neo and Air, carbon and BCN, is 7.5% to 8.5% shorter with the table than without it in LAMMPS). It still accepts one interval: spin Air at 129,505 to 129,536 nodes, where the sustained gain is −6.9% for carbon. Repeated eight times per row with the node types of the tuner and lead-ins of 500, 1,500 and 3,000 ms (Air preset at 100,800, 129,536 and 131,072 nodes), this check accepts the per-layer kernels in none of 72 repeats. If the repeats are independent, that bounds the rate of false acceptance by 4.1% at 95% confidence, in line with its one false acceptance among the roughly 80 checks of a freeze.
- `5c5720427` (`fix(dpa4c): keep the fitting routes that do not lose on trains`) requires only a positive mean gain, because on a V100 at its 300 W limit the requirement of 1% refuses gains that LAMMPS shows (the commit message gives the measurement). On the L20 it accepts the per-layer kernels in 14 of the 48 repeats at 129,536 and 131,072 nodes (7 of 16 at 500 ms and 2 of 16 at 3,000 ms). The mean gain over these repeats is about −0.7%, and the mean of two captures scatters by about 0.9 points. The per-capture gain scatters by 0.7 to 2.3 points at these sizes against 0.3 to 0.5 at 100,800 nodes. With one node type the order of the routes within a capture also moves its result. The SM clock in the last 0.4 s of the per-layer train that opens the second capture is 2,190 to 2,340 MHz, against 2,120 to 2,190 MHz for the per-layer train that follows the rules' train in the first capture (clocks reconstructed as in section 11.6.2). The second capture shows a loss smaller by 0.9 to 5.7 percentage points. In the blocks with carbon nodes at 129,536 nodes, the difference falls with the lead-in (3.6, −0.5 and 0.3 points at 500, 1,500 and 3,000 ms), and so does the standard deviation of the mean (1.4, 0.4 and 0.3 points). With the node types of the tuner at 131,072 nodes the difference is +0.7, −1.3 and −2.3 points at the same lead-ins, and the standard deviation of the mean stays at 0.7 to 1.1 points at 129,536 and 131,072 nodes. No later version depends on this effect for one type, since every one of the 64 repeats with one type is negative in the mean of the two captures (−2.6% to −8.4%).
- `e892bbbe6` (`fix(dpa4c): check the fitting routes on trains of two node compositions`) times both compositions and requires a positive gain on each, as the composition measurement of section 11.6.2 calls for.
- `867480bd1` (`fix(dpa4c): hold the fitting routes to the tie on trains`) holds a candidate to the tie of the screen instead of to zero, and tries every candidate in turn instead of the best one only. On a V100 at its 300 W limit the per-layer kernels of the trained Mini at 10,296 nodes gain 0.3% to 1.1% on trains, within the scatter of two captures. The requirement of a positive gain refused them in some freezes although they shorten the LAMMPS step there (the commit message gives the measurement). The earlier check also left the next candidate untried where the best one failed.
- `f5f9e6a39` (`fix(dpa4c): settle every fitting route before a sample stops`) changes the stop rule of the screen. A sample stops taking alternating captures only where every route besides the rules' lies beyond the margin of its stage; the earlier versions stopped once the route of the largest median gain was settled. Every route that exceeds its own bound is a candidate, so that a runner-up within the margin of its bound could depart from the rules on three captures where seven would have left the run size to them (the commit message gives an example).

### 11.7 Runtime environment

The block between `# >>> deepmd-kit runtime >>>` and `# <<< deepmd-kit runtime <<<` of the five files that a shell of root reads, `/root/.bashrc`, `/root/.profile`, `/root/.bash_profile`, `/root/.zshrc` and `/root/.zshenv`, exports `LAMMPS_ROOT=$HOME/Software/lammps/lammps-outisli`, puts its `bin` first on `PATH` and exports `LAMMPS_PLUGIN_PATH=$DEEPMD_CPP_ROOT/lib/deepmd_lmp`. Root's login shell is zsh, which reads `.zshenv` and `.zshrc`. A bash login shell reads `.bash_profile` and skips `.profile`, so that `.profile` serves a login shell of another kind, which was not tested.

Every block puts the `lib64` and `targets/x86_64-linux/lib` directories of the CUDA toolkit on `LD_LIBRARY_PATH`, and the block of `.zshenv` also puts the `nvidia/cu13/lib` of the base environment there. No file puts a directory of the C++ prefix on `LD_LIBRARY_PATH`, since a Python process could then load the libraries of the C++ prefix instead of those of the Python package; the plugin finds its libraries through its RUNPATH.

In a fresh login shell (`env -i`, `zsh -l -i` and `bash -l -i` alike) `lmp` resolves to the fork, `LAMMPS_PLUGIN_PATH` names the plugin directory, and a Neo run at 10,296 atoms through `lmp` exits with status 0 and writes the run-0 dump of the harness run bit for bit.
