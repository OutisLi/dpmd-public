Notes of the port to the Bohrium V100 development container: the device and the host, the build configuration, the environment hazards of the container, the baseline correctness and timing of commit `37a3fa54c`, and every tuning decision with the measurement behind it.

## 2. Build configuration

The operator libraries carry sm_70 code alone: `CMAKE_CUDA_ARCHITECTURES=70` and `DEEPMD_CUDA_PORTABLE_PTX=OFF` give 125 sm_70 images and no PTX in `libdeepmd_op_pt.so` (`cuobjdump --list-elf`). The torch CMake configuration ignores `CMAKE_CUDA_ARCHITECTURES` and derives its own `-gencode arch=compute_70,code=sm_70` from the device.

Host code is not tuned to this CPU, because the container is imaged for Bohrium jobs on hosts with other CPUs: both build trees, the editable install (`build/py37-none-linux_x86_64`) and the C++ interface (`source/build`), are configured with `ENABLE_NATIVE_OPTIMIZATION=OFF`, carry empty `CMAKE_CXX_FLAGS` and no `-march=native` in their `build.ninja`. The CPU DPA4C kernels keep their per-unit instruction-set pins (`x86-64`, `x86-64-v3`, `x86-64-v4`) and select one at run time; this host takes the AVX-512 kernels. Every library of the Python package and of the C++ prefix carries a RUNPATH (`$ORIGIN`, and the torch library directories for the C++ interface) and no DT_RPATH.

Build times on the 12 threads: the editable install 872 s (181 steps, of which the DPA4C shards `c128_l2`, `c128_l3`, `c128_l4` and `c32_l234` take 650 to 800 s each), the C++ interface 1,008 s, and its rebuild without native host tuning 85 s (65 host objects, no device code).

The LAMMPS fork of the baseline measurements, with the DeePMD-kit styles built in, is built as `doc/outisli/install.md` section 3.1 describes, with `Kokkos_ARCH_VOLTA70` and `MPI_CXX_COMPILER=/usr/bin/mpicxx`, in a clean environment (section 3): its `CMAKE_CXX_FLAGS` and linker flags are empty, so the host code takes GCC's x86-64 default; zlib is the system library and FFTW3 is absent, so the host FFT is KISS. `lmp` and `liblammps.so.0` carry a RUNPATH alone (the library directory of the fork, the DeePMD-kit prefix, Open MPI and `/usr/local/cuda/lib64`). Under the `LD_LIBRARY_PATH` of the harness (`BENCH_DP_LIB`, `BENCH_TORCH_LIB`, then the login path) the executable binds its own `liblammps.so.0`, the DeePMD-kit libraries of the prefix, the system `libstdc++`, zlib and Open MPI, the `libgomp` of torch and the `libcudart.so.12` of the 12.6 toolkit. The build takes 1,550 s and its configuration 22 s.

## 3. Environment hazards of the container

- Locale. The container holds only the C, C.utf8 and POSIX locales. Under the `en_US.UTF-8` that ssh forwarded from the client, `import readline` segfaults in conda's Python 3.13.5 with readline 8.2, and pytest with it (exit 139 in `_pytest/capture.py`). The ssh client now sends `LANG=C.UTF-8 LC_ALL=C.UTF-8`.
- conda activation. A `bash -c` started under sshd (`SSH_CLIENT` set, or standard input a socket) at a shell level below two sources `~/.bashrc` (Ubuntu's `SSH_SOURCE_BASHRC`), whose interactive guard is commented out; its conda initialization activates the base environment and exports conda's `CFLAGS`, `CXXFLAGS`, `LDFLAGS` (`--disable-new-dtags`, `-rpath /root/miniconda3/lib`), `CONDA_BUILD_SYSROOT` and `NVCC_PREPEND_FLAGS` (`-ccbin` of conda's g++ 11.2). `CC` and `CXX` stay the system compilers, which `~/.bashrc` exports afterwards. A LAMMPS build configured in that environment takes `librt` from conda's CentOS 7 sysroot, whose `libm.so` linker script names `/lib64/libm.so.6`, and fails to link `liblammps.so.0`; a build that links carries a DT_RPATH, which the loader searches before `LD_LIBRARY_PATH`. Jobs are therefore launched with the ssh variables unset, standard input from `/dev/null` and `bash --norc`, and the build scripts refuse to run while any of these variables is set.
- `LD_LIBRARY_PATH` of the login environment lists the CUDA 12.6 toolkit directories before `site-packages/nvidia/cu13/lib`, which holds CUDA 13 libraries under the sonames of CUDA 12 (`libcusparse.so.12`, `libcufft.so.12`); the toolkit copies come first, and torch loads its own through its DT_RPATH. Torch and the toolkit are both CUDA 12.6, so `machine.sh` leaves the path unchanged.
- libstdc++ of the base environment. The image ships `libstdcxx-ng` 11.2.0 of the defaults channel, whose `libstdc++.so.6.0.29` runs the destructors of `thread_local` objects without glibc's `__cxa_thread_atexit_impl`; a Python process that loads a charge-conditioned compressed DPA4C archive, such as `gen_dpa4c_canonical.py` and a `DeepPot` evaluation of its archive, ends with SIGSEGV after its work (exit 139), because the destructor of a `thread_local` of the AOTInductor wrapper of the charge-state fold runs after the wrapper is unloaded. The repair installs `libstdcxx` and `libstdcxx-ng` 15.2.0 of conda-forge (`libstdc++.so.6.0.34`, `GLIBCXX_3.4.34`, which binds `__cxa_thread_atexit_impl`) in place of that `libstdcxx-ng`, takes `packaging` 26.3 and `setuptools` 81.0.0 over from pip into conda-forge records at the same versions and reinstalls conda 26.1.1 at its build, so that conda transacts in the base environment again. Afterwards both processes exit 0, the energies of the archive under its three charge states are those of before and the other outputs lie within the run-to-run spread of Python canonical inference measured before (9.8e-8 relative), `install.sh --verify`, the CPU suite and the LAMMPS dumps, which link the system libstdc++, are unchanged. The check before the cleanup of section 15 found `libstdc++.so.6` of the base environment resolving to `libstdc++.so.6.0.34` (`GLIBCXX_3.4.34`); the files of the repair are hard links of its package cache in the scratch directory of the port, which the cleanup removed, so their content stays, their link count fell from 2 to 1 and the `conda-meta` records of the repair name cache paths that no longer exist, the state that `conda clean --all` leaves.
- Profiling. Nsight Compute cannot read the performance counters: `ERR_NVGPUCTRPERM` with 2024.3.2 and 2025.1.1 (`RmProfilingAdminOnly=1`, and the container lacks `CAP_SYS_ADMIN`), and the default `ncu` 2025.4.1 reports in addition that the GPU is not supported. Nsight Systems 2024.5.1 traces the kernels.

## 5. Register state of the edge kernels on sm_70

Compute capability 7.0 takes the `#else` branch of `edge_resident_blocks` (`graph_compress_launch.h`), whose values were measured on 9.0: 24 resident blocks for the spin kernels of degree two and 32 for the others, which leaves a one-warp block 64 registers per thread. In the installed library 1,246 of the 1,720 `edge_backward_kernel` instantiations and 701 of the 1,728 `forward_kernel` instantiations keep a stack frame, of up to 312 and 112 bytes; the readout and node-backward kernels keep none (`cuobjdump --dump-resource-usage`).

## 7. Register budgets of the edge kernels

The edge kernels of independent rows take the launch bound `edge_resident_blocks / (Warps * Split)`, whose `#else` values were measured on 9.0: thirty-two blocks, sixty-four registers per thread, for every spin-free kernel. Three libraries of the scratch tree give that bound an sm_70 branch: `base` (the `#else` rule, which reproduces the installed library bit for bit), `free` (no bound, the compiler's own count) and `r80` (twenty-four blocks, eighty registers).

At sixty-four registers the edge backward of every spin-free profile keeps a stack frame of 40 to 224 bytes, which `free` removes entirely, so the frames are spills: Nano 72 to 88, Mini 104, Neo 40 to 64, Air 160 to 176 and Plus 200 to 224 bytes; the forward of Nano keeps none, those of the others up to 104 bytes. `r80` removes the spill of the degree-two profiles but for 8 to 24 bytes in the low-rank scans of Neo, and halves that of Air and Plus (88 to 128 bytes). The slotted kernels keep their own bound (`slot_resident_warps`, 96 or 128 registers) and are unchanged.

The Mini anomaly of section 6 is the spill. Carbon and BCN launch the same Mini instantiations, `forward_kernel` and `edge_backward_kernel<32, 2, false, false, false, true, unsigned int, 1, Split, Scan::Direct>`, whose run-time flag `folded = single_type(args, radial_modes) >= 0` selects the single-type walk on carbon and the pairwise walk on BCN; only the single-type walk keeps the sums of the extra feature live through the edge loop. Under Nsight Systems at 10,296 atoms the Mini edge backward takes 1.006 ms on carbon and 0.472 ms on BCN with `base`, and 0.370 and 0.408 ms with `r80`; the carbon step then takes 1.745 ms against 1.917 ms on BCN.

The spin campaign of `free` shortens the spin step of Nano by 13% to 22%: its degree-two spin backward spills 104 to 128 bytes at the eighty registers of its twenty-four blocks and none at the compiler's 120 to 124 registers.

Effect on the outputs. The row split of a small system follows from the occupancy of its scan kernel (`row_split`), so a budget changes the split of the systems below one wave of resident warps: at 512 atoms, the dumps of carbon (all grades), BCN (Nano, Mini) and five elements (Nano, Mini, Neo) differ from `base`, with relative force deviations of 1.2e-6 to 2.3e-6 in `bench_ops`. Under every forced `DP_DPA4C_ROW_SPLIT` (1, 2, 4, 8) `r80` reproduces `base` bit for bit, on carbon in `bench_ops` and on BCN and five elements in the LAMMPS dumps, and at 10,296 and 100,800 atoms, where the split is one, every output is unchanged. `free` changes in addition the code of the split-one folded low-rank forward of Plus (1,029 FFMA and 119 FMUL against 908 and 116), whose outputs depart by 7.4e-7 at the forced split one.

The adopted rule of the sm_70 branch is twenty-four blocks for every spin-free kernel, and for the spin kernels twenty-four blocks for the degree-two forward and the degree-two backward of 64 channels or more, the compiler's own count for the degree-two backward below 64 channels, and the thirty-two blocks of the `#else` branch for the degree-three kernels, which serve only systems of more than eight node types and the generic graph path and are not measured here.

## 8. Launch choices

The overrides stage with the rows in increasing bond length (`--order distance`, model-only, carbon) confirms the co-scheduled blocks: without them Air and Plus take 58.0% and 68.2% (Air) and 47.2% and 58.7% (Plus) longer at 10,296 and 100,800 atoms, although their co-scheduled kernels spill 136 to 184 bytes at eighty registers. Single-process model-only times spread by up to 8% at 512 atoms here, so a choice below that margin is decided by a LAMMPS A/B.

At 512 atoms of carbon the derived split of the folded scans of Air and Plus is four: their scan kernels keep thirty-two one-warp blocks per SM at sixty-four registers, 2,560 warps on the 80 SMs. A LAMMPS A/B (six alternating rounds, ranges at most 0.8%) gives the forced split two 11.2% (Air) and 11.0% (Plus) and the forced split one 7.5% and 9.8% shorter steps; on BCN, whose slotted kernels of 128 registers derive two, the forced split two equals the derived choice and the forced split one is 8.9% and 9.1% longer. Under the twenty-four blocks of the adopted budget the same rule derives two on carbon.

## 9. Fitting network

The fused fitting network streams its weights with `cp.async` and is declined for images below compute capability 8.0, so every run takes the per-layer kernels. At 10,296 atoms they take 26% to 40% of the step (Nsight Systems: 0.33 ms for Nano, 0.70 to 0.73 ms for Mini, 0.92 ms for Neo, 0.95 ms for Air and 2.12 to 2.15 ms for Plus, the same on carbon and BCN).

The fused kernel compiles for sm_70, where `copy_async16` copies synchronously. A scratch build that accepts images of version 7.0 for every shape, skips every shape whose dynamic shared memory exceeds the opt-in of the device (98,304 bytes here, against the 101,376 bytes that the compile-time bound of the shapes allows: the width-256 throughput shape takes 98,944 bytes) and emulates the fp32-ridge rule of the L20 port for widths of 256 and 384 returns the outputs of `r80` bit for bit (`bench_ops` at three sizes, the 30 LAMMPS dumps), and the fused-network test of `test_dpa1_cuda.py`, which skips on the per-layer-only build, passes with 256 subtests. At 1,728 and 2,352 atoms the runs take the latency shapes (54 and 74 panels), which run each panel alone on its multiprocessor and keep the weight stream ahead of their FMAs only through the asynchronous copies of their ring: on this device only width 96 still gains there, and Plus at 54 panels, whose pass leaves 26 SMs idle, takes 17% longer. The adopted port therefore serves the throughput shapes, whose co-resident panels hide the weight stream behind each other, on images of compute capability 7.0 and later and the latency shapes on images of 8.0 and later; on this device every latency run takes the per-layer kernels.

The width-192 throughput shape keeps two CTAs per SM, 160 panels per wave, so its gain follows the fill of the last wave: on carbon Mini takes 7.3% less time at 9,680 atoms (303 panels, the last of two waves 89% full), 0.4% less at 12,320 atoms (385 panels, the last of three waves 41% full) and 2.9% more at 10,296 atoms (322 panels, the last of three waves 1% full), and 2.6% less at 100,800 atoms. Three cases are left to the route tuner of the fitting, which measures the routes on the device at freeze time: the low-fill waves of the width-192 throughput shape, the latency shapes of width 96, which would shorten the Nano step by 4% to 5% at 1,728 and 2,352 atoms, and the native-spin Mini. The spin descriptor of Mini has 207 features against its hidden width of 192, so the layer-0 backward of the fused network contracts in several passes, and the fused network lengthens the Newtonian spin step of Mini by 6.2% at 10,296 atoms and by 1.3% to 1.4% at 100,800 atoms on carbon and BCN (LAMMPS A/B of the build with and without the fused network, four alternating rounds), while it shortens that of Nano, whose spin descriptor stays below its width of 96, by 8.4% to 8.5% and 4.2% to 4.4%. The tuner sends the spin Mini to the per-layer kernels at both sizes on this device; H20 measures the spin Mini 2.0% faster fused at 10,296 atoms, so the choice follows the device and the input width together.

## 10. Graph build

The single-pass fill of the benchmark systems is the kernel of up to twelve candidates per lane; without `cp.async` it stages the entries of a center in registers, and at the sixty-four registers of its bound of four teams per SM it keeps a 64-byte stack frame (the kernel of sixteen candidates, three teams, 56 bytes at eighty registers). It takes 174 µs at 10,296 atoms (Nsight Systems), 18% of the Nano step.

A bound of three teams per SM for the kernel of twelve candidates, eighty registers at twenty-four warps, would remove its spill at the cost of eight resident warps. The fill takes 18% of the Nano step at 10,296 atoms and less of the steps of the larger grades, so such a bound could shorten the Nano step by a few percent at most; the bounds are compile-time arguments of `Kokkos::LaunchBounds` in the adapter, an sm_70 value would follow `KOKKOS_ARCH_VOLTA70`, and every alternative takes a build of the fork of 26 minutes, so the direction remains open.

Kernel times of single Nsight Systems runs at 512 atoms are not comparable between runs on this container: the persistence mode is off, the SM clock falls to 135 MHz between processes, and the default window of `lmp_nsys.py` (50 warmup and 100 timed steps, about 60 ms of device work at this size) can close before the clock has risen. In one run every kernel took 1.4 to 2.2 times as long as in another of the same system, steadily through the run (the fill 61.4 µs against 27.6 µs), so absolute kernel times at 512 atoms are taken after a warmup of 2,000 steps (`lmp_nsys.py --warmup 2000`), and a single run gives the shares of its own step only. The LAMMPS campaigns, which time 2,000 steps per run in alternating rounds, resolve differences of a fraction of a percent.

## 12. A data race in a Triton kernel of the compiled training graph

The failure is reproduced by a replica of the test that runs both parametrizations in the order of pytest on a fresh copy of the Inductor cache of the failing campaign process: it fails in 4 of 7 runs with the caching allocator filled with NaN before each parametrization, in 3 of 3 with it filled with all-ones bytes and in 1 of 5 without filling, and in neither of 2 runs on an empty cache. The wrong gradients belong to the compiled graph of the vacuum-reference model alone. Against an eager float64 reference on the CPU, the eager padded and ragged sides agree to 4e-14 normwise in every run, while the compiled call that fails departs by 1.9e-3 to 2.4e-3 in 15 of the 20 parameter gradients, up to 0.53 relative in single elements. In the test's own sequence the ragged call fails; in longer series of single compiled calls a padded call fails as well, since both layouts reach the same compiled modules on the same 14-node graph: the padded path compacts its 21 slots before the compiled call. The wrong values recur as a few patterns, identical up to the last bits of two atomically accumulated arrays, under NaN filling, all-ones filling and none, so they contain no byte of the filling.

What the failure is not: the saved tensors of a failing call keep their storage digests between its forward and its backward; compute-sanitizer initcheck with the caching allocator off reports no error and racecheck no hazard; at 14 nodes no view of the four generated modules reaches beyond its storage, no storage is reused while an earlier view of it is live, and no donated saved tensor shares its storage with another saved tensor or output; and the generated code calls no DeePMD-kit operator.

A trace of every launch localizes it. After every launch of the compiled graphs a hook copies each tensor that the kernel writes to the host, and the inputs of every graph call, through host copies of their storages (no device allocation), and every call is held against the trace of a passing call of the same layout. In every failing call the forward and the backward agree with the reference up to the one launch of `triton_red_fused_add_bmm_permute_slice_transpose_view_50` in the backward, whose output `out_ptr1` departs in rows 9, 11, 12 and 13 of its 16 (the two vacuum rows, 14 and 15, are correct); every later departure follows from that output. The nine inputs of that launch equal those of the passing reference bit for bit, and every argument lies inside its caching-allocator block. The kernel fuses six bmm reductions over nine columns of the 16 node rows (FX source nodes `slice_170` to `bmm_139`); the lines of its Triton source that produce `out_ptr1`, verbatim:

```text
    r0_numel = 9
    xmask = xindex < xnumel
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):
        r0_mask = r0_index < r0_numel
        tmp0 = tl.load(in_out_ptr0 + (r0_1 + 9*x0), r0_mask & xmask, eviction_policy='evict_first', other=0.0)
        tmp1 = tl.load(in_ptr0 + (r0_1 + 9*x0), r0_mask & xmask, eviction_policy='evict_first', other=0.0)
        tmp6 = tl.load(in_ptr2 + (r0_1 + 56*x0), r0_mask & xmask, eviction_policy='evict_first', other=0.0)
        tmp2 = tmp0 + tmp1
        tmp11 = tmp2 * tmp6
        tmp12 = tl.broadcast_to(tmp11, [XBLOCK, R0_BLOCK])
        tmp14 = _tmp13 + tmp12
        _tmp13 = tl.where(r0_mask & xmask, tmp14, _tmp13)
        tl.store(in_out_ptr0 + (r0_1 + 9*x0), tmp2, r0_mask & xmask)
    tmp13 = tl.sum(_tmp13, 1)[:, None]
    tl.store(out_ptr1 + (x0), tmp13, xmask)
```

Recomputed on the host from the inputs of the failing launch, with the intended sums and again with the kernel's own index and mask expressions applied to the raw bytes of each argument's allocator block, `out_ptr1` equals the reference to 7e-18, so the indexing and the masks are right. In every wrong row of three failing launches the written value is the reference plus exactly `in_ptr0[x, 8] * in_ptr2[x, 8]` (ratios 1.000000000000000 to 1.000000000000001 in rows 9, 11 and 12, and 1.0000000000001 in row 13, whose error is 4e-11): the term that the load of `in_out_ptr0` adds when it returns the sum `tmp2` that the kernel itself stores to the same address in the same iteration.

The Inductor cache of the failing process holds for this kernel `XBLOCK` 16, `R0_BLOCK` 4, `num_warps` 8, `num_stages` 1: 256 threads on a 16 x 4 block. Its layout, `#blocked` with `sizePerThread` [1, 1], `threadsPerWarp` [8, 4] and `warpsPerCTA` [8, 1], gives warps 0 and 1 the block and warps 2 to 7 three copies of it. In the PTX every load is issued by all 256 threads (`@%p1 ld.global`, `p1` the row mask of the first iteration), the in-place stores by the first copy alone (`@%p2 st.global`, `p2 = ((tid & 192) == 0) & p1`), and no `bar.sync` lies between the loads of an iteration and its stores; the only barriers are those of the cross-warp epilogue, which gathers the partial sums of all copies through shared memory. A copy that runs behind the first loads the stored sum, and the epilogue can take that copy's partial sum: a write-after-read race inside one program, in the lowering of Triton 3.7.1 under a replicated layout. The stored block stays correct. The two runs on an empty cache tuned the kernel to `XBLOCK` 2, `R0_BLOCK` 16, `num_warps` 2, whose 64 threads hold the block once in a single iteration, while the cache of the failing process, every copy of it and the caches recompiled from those copies, which keep the tuned choice of an unchanged kernel, hold `num_warps` 8. The timing of the autotuner decides between the configurations, and a cache keeps its decision for every later process.

Two standalone scripts, which need neither DeePMD-kit nor torch.compile, reproduce it: `debug/cuda_bench/devices/v100_triton_race/triton_inplace_race.py` (md5 `2303a9f3`), the pattern in a few lines of Triton, and `triton_k50_exact.py` (md5 `ee305f90`), the kernel verbatim at its cached configuration on fresh buffers in the layouts of the compiled graph, on the arguments of a failing launch or on drawn values. The mechanism is inferred. Under lazy module loading, the default of CUDA 12.2 and later on Linux, the runtime loads a kernel when it is first launched or referenced, `cudaFuncGetAttributes` is such a reference, and loading a kernel allocates device memory for its code (CUDA C++ Programming Guide, Lazy Loading). The queries of the untuned archive therefore load the queried fused kernels ahead of every DPA4C kernel, and every kernel that the process loads afterwards lies elsewhere in device memory than in a process that skips them. Under eager loading, which loads every kernel at start-up, both archives take as long as the tuned one or longer and spread by 2.6% to 5.3% between processes, so the short step of the untuned archive follows from its lazy load order and not from the attribute settings, which it makes under eager loading as well. Whether the placement of the code or that of the data allocated after it moves the kernel times is not measured, since Nsight Compute cannot read the counters in this container (section 3). At 512 atoms each layer kernel of Mini runs 48 CTAs, at most one per multiprocessor.

Two builds or archives whose call paths differ in device queries, and therefore in the order in which their kernels load, are thus not comparable at small sizes on this device: identical DPA4C kernels change their time by 1.6 to 4.9 µs, faster or slower, and the step by up to 2.8% at 512 atoms, a difference that every round of an alternating A/B reproduces. A comparison at such sizes holds the query path fixed, or attributes a difference to the change under test only against a control that changes the query path alone, as `DP_FITTING_FUSED=0` does here.

The table of the tuner therefore names a route only where its measurement departs from the rules and holds the rules (choice 0) for every other run size, so that a tuned archive takes the call path of an untuned one wherever the two agree. The screen of the tuner times the routes in alternating short bursts on a periodic bulk system of exactly the run size, whose nodes take three types drawn among the first three of the model. A route other than that of the rules is a candidate where its median gain over the rules exceeds its bound, the larger of the tie of 1% and the half-range of its per-capture gains. The sample times one capture and stops there only where every route besides the rules lies more than 4 points below its bound; otherwise it takes three captures and stops there only where every route lies more than 1.5 points from its bound, above or below; otherwise it takes seven. A departure from the rules rests on at least three captures. The candidates are checked on trains of one route at a time, in the order of their gains: each train is timed after at least 500 ms of device time of its own replays, in two captures that time the routes in opposite orders, first with every node of type 0 and then on the three types of the sample. The first candidate whose median gain over the rules on the trains is at least -1% on every composition takes the run size, and the check of a candidate stops at the first composition on which its median gain is below -1%; where no candidate holds, the rules keep the run size. A model of one node type trains one composition. Between two routes of which neither is that of the rules, which the bisection of a band compares, the trains alone decide: the second route wins where its median gain over the first, averaged over the compositions, is positive.

The second composition follows from the L20 port, where a board at its 350 W limit showed that the loss of a route that draws more power depends on the number of node types of the system and not on the element, and that the composition which shows it differs with the run size: the per-layer kernels lose 4% to 8% at 129,536 to 131,072 nodes with one node type (H, C or Fe) and about 0% to 1.5% with three, and a trained Air model at 12,320 nodes gains 1.1% with one node type and loses 1.4% with three; below the power limit the gain does not depend on the composition. The one-type series of the probes above is carbon, whereas the check uses type 0 of the model (hydrogen in the trained Mini); the probes do not test whether the two give the same gain.

The check holds a candidate to the tie of 1% on the trains, and not to a gain above zero, because the gains of the per-layer kernels on trains are of the size of the scatter between captures.
